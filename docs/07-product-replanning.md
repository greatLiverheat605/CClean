## 2. 产品定义与范围

建议定位：**本机 Agent 开发空间管理工具**。帮助用户理解开发工具及项目占用与增长、判断内容用途和处理影响，并对已验证对象完成用户确认的清理。

主流程：

> 发现占用和增长 → 查看相关工具、项目与活动证据 → 理解文件用途与价值 → 选择保留或处理 → 预览并确认 → 查看结果及后续影响。

### 全磁盘与全部 Agent 的含义

- 容量总览、盘点、观察范围、清理估算和执行结果都按真实卷显示，不再固定写成 C 盘。
- 一个项目可以关联多个磁盘上的工具和缓存；一个缓存可能涉及多个项目。统计和保护不能假设一一对应。
- 清理某一卷的对象只能计入该卷结果；父子目录、同一文件身份不能重复累计。移动盘断开、盘符变化或目录迁移后重新核验范围，并保留观察缺口；不同文件系统的观察、计量与删除能力分别验证。
- 推荐范围来自可说明的发现证据，逐项展示来源与识别程度；项目路径本身不足以证明某个缓存仅属于该项目。
- “覆盖本机所有 Agent”作为兼容目标：维护已识别工具/版本能力，提供自定义工具与目录纳入方式。未识别、无权限、未扫描和不支持的环境要可见，不能称“已找齐”。
- 通用纳入解决可观察性，不自动授予清理资格，也不代表具备会话识别或精确进程归因。
- 盘点范围与持续观察范围分别展示。用户可先盘点本地磁盘，再确认持续观察的项目和相关目录。
- 用户已确认先覆盖 Windows 本机运行的 Agent；WSL、Docker 内部发现、追踪与清理后续再做。已有 Windows 侧旧 WSL 转储规则属于宿主普通文件处理，不能据此宣称支持 WSL 内部能力；该规则是否继续纳入新版清理按规则评审处理。
- 共享网络盘、远端机器和虚拟磁盘内部能力不能从“本机所有 Agent”自动推导为已确认支持。

源码、配置凭据、Git/Agent 持久数据与未知对象保留原有保护边界。未来扩展清理规则须单独证明用途、恢复代价和安全条件，不能用扩大删除范围代替工具兼容。

## 4. 内容解释与用户选择

### 分类结构建议

“用途”“当前能否处理”“依据是否充分”分开表达，避免再次用“工具 / 临时目录”混合持久历史与临时产物。

用途初始分类可包括：项目源码与工作成果、配置/凭据、Git 与 Agent 历史、已安装依赖、可重建构建产物、下载缓存、日志/故障转储、尚未识别内容。分类识别不依赖读取用户秘密或对话正文。

每个可操作类别至少说明：

1. **是什么、做什么用**：用用户能理解的名称，必要时说明所属工具及版本。
2. **与谁相关**：关联项目/会话/其他消费者及依据；共享或未知关系明确展示。
3. **为什么建议处理或保留**：说明规则证据、观察时段及其局限。
4. **删除会怎样**：是否失去诊断/历史、需要联网、影响离线使用或下次构建。
5. **如何恢复或重建**：给可靠方法；永久丢失和仅可重新生成要区分，未知代价不能编造时长。
6. **空间与范围**：所在卷、已知占用、本次候选量、尚未检查的部分。
7. **用户控制**：保留类别/具体项、调整本次选择、记住类别偏好、查看原位置。

偏好命中只改变建议或默认选择；配置/规则/影响发生变化时重新解释。未知和不满足安全条件的对象不能通过偏好或全选绕过保护。

对象有关联依赖时，用户的逐项保留必须尊重组合完整性。例如 npm 内容与索引的配套要求，需要一同展示影响范围；无法形成可靠组合时给出原因并停止执行，不能悄悄加入未批准对象。

真实盘点补充的设计约束：Claude 的 `LocalCache` 混有运行镜像和会话磁盘，Codex 的 `.cache` 主要为运行时，`artifacts` 混有可生成产物与验收证据。分类必须落到能解释用途的子范围，不能按父目录名称整体归为垃圾。本次 CClean 压测数据按 D-11 验证候选，专用构建目录继续只读核验；历史、交付、回退版本和验收证据分别保留其价值判断。

## 5. 关键操作闭环

| 流程 | 预期行为与完成定义 |
| --- | --- |
| 首次使用 | 看见本机磁盘概况；发现/选择项目；给出相关工具数据和缓存推荐及依据；用户确认观察范围；说明历史从此开始 |
| 持续观察 | 手动启动后观察已确认范围；区分“已有快照”和“持续观察可靠”；关窗口进托盘，恢复同一实例及页面状态 |
| 定位增长 | 从磁盘/项目增长摘要进入时间线，再到涉及目录和文件；范围、时间和证据等级保持一致 |
| 清理 | 类别说明 → 调整保留/选择 → 形成有限清单 → 明确确认 → 实时处理状态 → 逐卷结果与历史 |
| 无候选 | 区分没有内容、未支持、仍活跃、观察不全、未配置等情况，并给出可行下一步 |
| 项目管理 | 支持调整监测范围、暂停及从管理列表移除；移除监测与删除实际文件明确区分，变更后的历史和保护状态有定义 |
| 版本比较 | 呈现独有文件、差异、相同内容和未确认项；保留建议能追溯依据，部分比较不能推出整个版本可删 |
| 退出/重启 | 明确退出停止后续清理并安全结束当前项，停止观察；重启展示空窗与中断状态，重新核查当前状态而不补造历史 |

精确写入进程、项目/会话上下文关联、共享、未知是不同证据。当前实现主要有上下文关联；更高精度的技术验证需单列，不能用自动会话发现代替写入证据。

### 轻量观察与按需增强追踪

Q-08 的运行方式已由 D-07 确认；以下行为作为设计与验收约束，增强追踪尚未实现，具体采集技术仍须 PoC 验证。

| 模式 | 用户行为与反馈 | 证据边界 |
| --- | --- | --- |
| 轻量观察（日常默认） | 手动启动应用后，按已确认的 Windows 本地各盘目录持续观察；可暂停、恢复、查看状态和缺口，关闭窗口后按 D-04 进入托盘 | 记录观察范围内的当前状态与变化，提供项目/会话上下文关联；不宣称已确定写入进程，不把文件大小变化当累计写入量 |
| 增强追踪（按需开启） | 用户手动开启与停止；开始前说明支持范围、可能的管理员权限和资源代价；运行中持续显示模式、范围、起始时间、健康状态和停止入口，结束后保留该时段的证据与缺口 | 只对已通过验证的采集场景提供进程级证据；无法关联、事件损失或权限受限的部分保留未知。进程与 Agent 聊天会话的对应关系需独立验证，不能由进程名称或同时活动推断 |

增强模式只从实际启动且采集有效的时刻开始提供证据，不追溯缺失历史，也不把此前轻量观察的上下文关联升级为进程证实。用户拒绝提权、采集启动失败或技术能力不支持时，保留可用的轻量观察并说明原因；增强过程中出现故障或事件损失时标记对应时段与范围，停止增强或回退不抹去这些缺口。

两种模式共用已确认的范围管理与现有保护边界。增强追踪得到更强来源证据，也不能单独授权删除、扩大规则白名单、取消活跃/未知保护或沿用已失效的清理确认。WSL、Docker 内部追踪仍按 D-06 留待后续。

| 独立验收组 | 必须观察的结果 |
| --- | --- |
| 轻量观察 | 普通权限下可观察已确认的本地目录；暂停/恢复、托盘/退出、跨盘与缺口行为准确。按交付版本单独验证资源和稳定性，原有失败记录不能被增强模式结果覆盖 |
| 增强开关与权限 | 手动开启/停止状态、实际采集生命周期一致；拒绝提权、启动失败或停止增强后，轻量观察仍可使用，未启动时不能展示虚假的进程证据 |
| 增强证据正确性 | 在受控写入中区分已证实、关联和未知；核验 PID 复用、子进程、并发写入、丢事件及故障，记录覆盖和未支持场景。进程关联与工具会话绑定分别验收，错误归因不得伪装成高覆盖 |
| 历史与资源 | 轻量、增强及无观察时段可区分；不补造停止或离线期间的写入历史。增强模式单独测量 CPU、内存和存储开销；可接受预算与覆盖目标根据 PoC 证据确定，未验证前不承诺精度或低开销 |
| 清理授权隔离 | 切换模式不增加可删除类别或自动执行；证据、活动或保护状态变化仍按现有规则重新判断，任何实际删除对应用户确认的具体清单 |

## 6. “细微 Bug 多”的验收方式

验收以用户可观察行为组织，每个实际发现记录“入口、范围、操作、预期、实际、修复版本、复验结果”。不以按钮存在、测试数量或完成页面数量作为交付结论。

| 验收组 | 关键场景 |
| --- | --- |
| 范围一致性 | 切换项目/磁盘/工具、父子目录、同名版本、分页筛选后，摘要、列表、选择与后续操作对应同一范围；共享内容不被错误重复累计 |
| 异步与反馈 | 扫描取消/失败/切页/重扫后，旧结果不覆盖新结果；未扫描、空结果、失败、不完整有不同说明；耗时操作显示进度并可取消，防止重复执行 |
| 偏好与执行 | 逐项保留确实改变最终清单；过期、活动变化、工具版本变化、新文件不能沿用旧批准；任何实际删除均对应本次确认；未处理项不能冒充成功 |
| 后台生命周期 | 关闭窗口不停止观察，明确退出不留采集；重复启动不产生重复监视器或执行器；托盘恢复可用，重启显示离线空窗 |
| 信息可信度 | 未知不等于安全，目录占用不等于可释放量，发现会话不等于活跃状态，时间接近不等于创建者证据，版本相同只限已验证对象 |
| 空间计量 | 区分逻辑大小、实际分配和本次预计释放；处理硬链接、父子范围、部分观察和运行时变化。以本机构建根逻辑 46.909 GiB、根内去重分配 42.023 GiB 为实例，不能把重复路径累计成清理收益 |
| 视觉与可操作性 | 常用窗口尺寸、125%/150%/200% DPI、深浅主题、键盘焦点、长路径与中文布局；重要说明和主要操作可见，选择与禁用状态清楚 |
| 跨盘与兼容 | 项目/缓存分盘、不同卷、不可访问目录、工具版本变化、工具未识别、磁盘不可用；统计和错误局限于对应范围，不能把缺口填成零 |

删除安全原有对抗测试、审计失败、真实 npm 重建与 watcher 链路仍须验收。当前 200 MiB 资源失败和新版多日观察缺项保留，后续按交付版本重新验证。

## 7. 建议实施顺序（尚未转为执行任务）

按 D-09 调整交付顺序：先完成空间解释与可控清理，再深化 Agent 活动追踪。以下阶段细分为工程建议；首批范围确认后再转成执行任务。基础观察与活动保护是清理前提，不能因追踪主线后置而跳过。

| 批次 | 目标 | 可评审产物 / 验收 |
| --- | --- | --- |
| R0：需求与界面定稿 | 明确本机环境边界、工具覆盖策略和核心操作 | 本文定稿、功能总表、低保真操作原型；用真实困惑场景验证是否看得懂、找得到、能选择 |
| R1：范围、解释与基础观察 | 统一磁盘/工具/项目/数据位置关系，让用途、影响和当前状态可信 | 发现完整度、逐卷统计、推荐范围依据、分类说明和未知状态；修复误导标签与陈旧入口；完成首批所需轻量观察、范围管理、托盘/退出/恢复及单实例基本行为，保留活跃/未知保护 |
| R2：可控清理与首批交付 | 让用户能理解影响、保留内容并成功完成有限清理 | 类别偏好、具体保留、固定预览、清理进度、逐卷结果与历史；验证自身删除通知和 npm 组合一致性风险；完成真实消费者重建、异常状态、相关 UI Bug、安装版本性能与稳定性及用户场景验收 |
| R3：Agent 活动追踪深化 | 完善活动联动、来源证据与按需进程级追踪 | 在基础观察上完善时间线和缺口展示；增强追踪先独立 PoC，再验权限回退、手动开关、证据正确性及资源预算，不因轻量模式通过就宣布增强可用 |
| R4：版本比较与整体验收 | 完善只读比较并验证各工作区联动 | 有依据的保留建议、跨工作区场景回归、交付版本性能/稳定性与用户验收；首批清理必需的验证须在 R2 完成，不延后到此阶段 |

技术上优先复用现有 WPF、Core、SQLite、监测与安全执行能力。现有一键计划 sub-028 中的相关任务可映射进 R2，但不得直接复制成新版全部范围。首批按 R0 → R1 → R2 收口；R3 的独立技术验证可在不拖延首批主线的前提下开展，具体并行度在任务拆分时确定。

R3 的增强追踪设独立技术门槛：先比较并验证 ETW 等候选技术在当前 Windows 环境中的权限、进程/文件关联、事件损失、覆盖限制与资源开销，再确定支持场景和产品接入方式。技术路线尚未冻结，PoC 尚未执行；旧 DEV-021 的延后状态不因本轮需求确认自动改为完成。PoC 不通过时继续交付经过验收的轻量观察，明确增强能力的未完成项，不降低归因证据要求。

首批交付的最低使用结果：用户能从已盘点内容判断用途、关联与处理后果，保留指定对象，核对有限清单并完成经验证规则的实际清理；成功、跳过、失败和逐卷结果分别可查。无候选或观察不足时说明原因与下一步。不得以页面完成、模拟数据或测试数量替代该结果，也不得把“识别全部 Agent”解释为其所有数据均可清理。

本轮不把旧版本实际整理、公开发行或任意未知文件永久删除纳入已确认范围。是否扩展更多清理规则，应按用户实际占用与验证成本排序，不先承诺支持数量或释放容量。
