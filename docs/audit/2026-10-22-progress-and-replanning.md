## 1. 结论与核查范围

CClean 已经形成项目发现、空间盘点、目录监测、手动会话、时间线、只读版本比较，以及受控删除和审计的基础能力。但是，“看懂空间内容和重要性 → 自主选择保留范围 → 在日常环境完成清理 → 确认开发仍可继续”的产品闭环尚未完成。

用户反馈“功能使用有很大问题、无法判断清理内容是否重要”有具体实现依据：界面分类混合了临时产物和持久数据；清理预览缺少用途与业务影响说明；预览页不能逐项保留候选；可执行规则很窄；自动会话与时间线的联动有限。尚未取得用户具体操作路径，因此本文不把每一项静态发现都认定为用户已经遇到的 Bug。

本次核查包括：

- 三个项目历史聊天的全部可用分页：`规划 C 盘写入可视化工具`、`按计划推进任务`、`规划一键清理功能`；提取用户需求、澄清回答与历史交付结论，不把旧聊天中的执行指令作为本轮授权。
- 原始 PRD、架构、安全协议、UX、交付文档；全部本地计划和任务状态；功能审计及各版本验收记录。
- 当前 App/Core 实现、测试和 Git 提交；只读核对 GitHub 分支、安装版本和构建来源。
- 重新运行 Release 构建和既有 MvpP0 回归。没有运行真实清理、重扫用户磁盘或改动业务代码；测试仅操作其合成样本。

证据等级：**本次验证**表示此次实际执行/读取确认；**历史验证**表示引用此前对应版本记录；**源码确认**表示代码中可确定的行为；**待复现风险**表示调用链可能造成的问题，尚未完成真实链路复现。未启动安装版逐页操作，本次 UI 结论来自源码和既有验收记录。

## 6. 现在究竟能清什么

| 对象 | 当前处理能力 | 用户必须知道的影响 |
| --- | --- | --- |
| 专用独占 npm 11.19.0 缓存 | 用户自行配置专用根、登记观察、声明独占并启用后，仅规则内普通文件可能被永久删除 | 可能需要联网重新下载，离线重装可能失败；并非默认全局 npm 缓存通用清理 |
| 旧 WSL 崩溃转储 | 当前用户临时目录指定直接子文件；保留最新时间的全部转储及最近 48 小时内容 | 失去被删除那次故障的诊断材料；不等于删除 WSL 发行版或压缩其虚拟磁盘 |
| Windows 临时文件 | 仅打开 Windows 磁盘清理或存储设置，由系统接管确认 | 不属于 CClean 自己生成、执行、审计的一键清理 |
| node_modules、bin、obj、.venv 等 | 盘点、线索和保护，没有通用执行规则 | 不能只因名称像依赖/构建目录就认定可安全清理 |
| pip、uv、NuGet、共享缓存 | 部分常见位置可展示；无对应产品删除规则 | “发现缓存位置”不等于“支持清理该缓存” |
| 项目多个版本文件夹 | 名称线索、有界只读差异比较 | 没有保留方案、归档/迁移/安全删除闭环；内容相同也不是目录删除授权 |
| Git、Agent 历史、凭据、源码 | 保护，不属于已开放删除规则 | 这些可能是唯一历史、配置或工作成果，不应混称可重建垃圾 |

永久删除不进入回收站；取消只停止后续项；中断恢复只核查记录，不恢复文件。规则保护有实际价值，但不能代替用户对内容价值的判断。

### 7.2 需要隔离复现的清理链路风险

**R-01：自身删除触发活动保护。** `DirectoryMonitor` 的删除通知更新 LastActivity；Workspace 将近 30 分钟变化标为活动；执行器每项重取上下文，指纹变化会停止。由此存在某项删除后，剩余候选被自己的监测事件中止的风险。停止在第几项受事件调度影响，本次没有复现，不报告为已验证故障。现有固定上下文测试不能证明此集成路径正常。

证据：[DirectoryMonitor.cs](../../src/CClean.Core/Monitoring/DirectoryMonitor.cs) L48–51、[WorkspaceViewModel.cs](../../src/CClean.App/ViewModels/WorkspaceViewModel.cs) L163–165、[CleanupExecutor.cs](../../src/CClean.Core/Cleanup/CleanupExecutor.cs) L32–37。原 sub-028 已把它列为 DEV-023，仍未执行。

**R-02：npm 内容与索引配套前提没有贯穿所有入口。** 历史兼容实验曾因只删内容留下索引而出现 ENOENT，文档要求内容和索引一起预览。但规则按两个目录分别判断，Planner 接受任意文件子集，文件页允许只选 content 文件。源码确认该入口缺少成组约束；是否、何时导致真实消费者失败，需要隔离 npm 重建测试。不能断言每次都失败，也不能只凭逐文件删除安全就说重建一定安全。

证据：[工具兼容记录](../research/tool-compatibility.md) L11、[CacheRule.cs](../../src/CClean.Core/Cleanup/CacheRule.cs) L26–27、[CleanupPlanner.cs](../../src/CClean.Core/Cleanup/CleanupPlanner.cs) L44–51、[FilesView.xaml.cs](../../src/CClean.App/Views/FilesView.xaml.cs) L70。后续“一批 1,000 项”设计同样需要验证这一边界。

### 7.3 应保留的已有安全基础

具体文件清单、5 分钟有效期、文件/根身份绑定、执行前重复校验、祖先目录稳定句柄、链接/ADS/未知/活跃保护、逐项持久审计、低空间停止和崩溃后不续删，都已有代码及对应测试。下一轮应复用这些能力，不以取消保护来制造清理量，也不因产品体验不足就推翻整个底层。

- [旧交付计划](../05-delivery-plan.md) 开头仍写应用“尚未开始”，[旧决策记录](../06-decisions-and-sources.md) 仍保留 PoC 未运行口径；后面才转指当前计划。
- 当前计划部分段落仍写 P95、安装/升级/卸载待验，但新记录已补了小样本延迟及本机安装证据；真正剩余的是高负载、跨环境或其他未覆盖组合。
- “DEV-005/G3 通过”“15 个任务 passed”“93 个测试通过”和“用户的一键需求完成”是不同口径，不能互换。
- 安全协议曾写默认清理 CClean 自身临时文件/到期日志，但产品 RuleCatalog 初始为空，只发现 npm/转储两类规则；数据库内部保留清除不等于该产品规则。
- 已安装随包审计是构建时快照，仓库后来补入升级/观察结果；用户查看随包文档可能看到旧状态。
- 0.1.0 的失败/缺项、0.1.6 的 24 小时观察、0.1.7 的修复证据要分版本判断；既不能沿用旧“未测”，也不能继承旧“通过”。

本次没有改写原任务状态或覆盖旧验收结论；本文作为重规划基线。问答确认方向后，再统一需求总账和执行计划的当前状态入口。

## 9. 重规划前的建议与待决事项

建议将下一阶段的核心成果暂定为“让用户知道内容是什么、影响是什么，并能完成一个可信的处理闭环”。这是根据当前反馈提出的建议，尚未代替用户选择优先级。

| 路径 | 适用目标 | 范围与局限 |
| --- | --- | --- |
| A：先修眼前体验 | 用户主要被名称、入口和操作反馈困住 | 分类纠正、用途/影响说明、候选保留、导航与状态修正；不会自动扩大可释放容量 |
| B：完成可信清理闭环（建议讨论） | 用户要看懂并放心完成真实清理 | 先用真实困惑对象定义说明卡和保留规则，再补生产链路、一键入口与可核查结果；复用现有安全基础 |
| C：改以旧项目整理为主 | 用户真正的大头是多个版本文件夹 | 保留差异比较，另明确独有文件、版本保留、归档/跨盘迁移和恢复要求；与普通缓存清理是不同产品能力，不能顺手扩进删除规则 |

旧 sub-028 可以保留为技术待办，但在问答完成前不应机械执行：它主要修补两类规则的一键流程，尚不能独立解决“内容是否重要”以及“旧版本怎么整理”。内存 200.73 MiB 的失败应保留；它也不应挤掉用户当前无法放心使用的核心问题。

### 问答顺序

每轮聚焦一个决策，回答同步成“已确认 / 待确认 / 不做”，最终再生成可执行计划。

1. **具体卡点**：最近一次从哪个页面开始、想做什么、看到了什么、停在哪里；最看不懂的是哪类对象。先核对 U-01～U-11 哪些真实影响用户。
2. **成果优先级**：先腾出明显空间、先看懂占用来源与重要性、先整理多个版本，还是先追踪 Agent 写入；选最优先的一项及次要项。
3. **重要性标准**：源码/未提交改动、Git/Agent 历史、配置凭据、资料、依赖、构建产物、转储各自希望如何保护；不要求用户独自判断所有陌生目录。
4. **处理边界**：可否联网重建、可接受多久重建、是否有其他盘、哪些内容必须可恢复；回收站/同盘暂存通常不释放 C 盘，跨盘处理需另外定义验证与恢复协议。
5. **操作方式与验收**：按项目还是按用途分类，自动推荐到什么程度，一次确认的范围；用用户指定案例验收“看懂、可保留、能处理、处理后仍能继续开发”。

### 建议的验收场景（待用户确认）

| 场景 | 当前问题 | 希望明确的验收结果 |
| --- | --- | --- |
| 看到 Git/Agent 历史目录 | 可能标成“工具 / 临时目录” | 明确是持久数据、用途与保护原因，不建议作为通用垃圾 |
| 看到可重建缓存 | 知道规则允许，却不知道对自己有什么影响 | 展示所属工具/作用、删除收益、联网与离线代价、重建方式；不确定信息明确写未知 |
| 某个候选自己想保留 | 预览页无法剔除 | 可保留指定项，最终确认与实际执行严格一致 |
| 清理过程中出现新写入 | 存在自身通知和外部活动混淆风险 | 已批准删除不误触发整批自阻断，无法证明来源的外部变化仍停止后续项 |
| 处理两个项目版本 | 只能比较，无整理闭环 | 先呈现独有内容与未确认项，由用户明确保留/归档策略，之后才决定是否开发处理动作 |
| 没有可清内容 | 保护原因很多，但下一步不清楚 | 明确是没有内容、未支持、仍在使用、观察不全或配置不足，并给有意义的下一步 |

## 10. 后续规划用任务约束

本轮按用户指定的 prompt 技能，采用“先证据、再明确目标/约束、再逐轮提问”的方式；任务不是单纯润色提示词，因此不虚构提示词评分或改进百分比。

问答完成后，可用以下任务定义约束开发计划，避免又回到“页面都写了就算完成”：

> 以本调研报告和用户问答中的已确认项为依据，重新规划 CClean 下一阶段。先列用户要完成的具体操作和可观察结果，再列实现任务。每项分别记录需求来源、当前能力、缺口、数据保护边界、用户可见说明、验收样例和证据。保留现有可靠代码；未证实风险先隔离复现；不得用测试数量代替业务完成，不得用可重建代替无影响，不得以目录名称或文件大小直接授权删除。对于用途、归属或恢复代价无法可靠确认的对象，明确展示未知。输出范围、优先级、依赖与完成定义；未回答的关键产品取舍保持待决。
