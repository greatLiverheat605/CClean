## 原问题与本轮边界

原 `Events()` 仅返回最早 3,000 条事件而不标记截断，`CleanupRecovery.Inspect()` 只看清单前 1,000 项，并对每项做一次 `LastOrDefault`。这两处在现有 1,000 项预览下常被遮住，但不构成可放大的完整历史读取协议。原写入以 UTF-8 字节限制 8 MiB，读取却检查字符数；两者单位不一致。

本轮清单 / 分页变更不放宽 Planner / Executor 授权边界，不修改规则、活动保护或生产句柄 share；此前开始前取消修补见 [R1-009 记录](first-release-r1-009.md)：预览最多 1,000 项、超过标记截断且执行拒绝；5 分钟批准有效期仍从原创建时间起算；8 MiB 持久清单和原审计空间预算保持。分页不续期，不追加候选，不生成可重放的执行计划。当前文件缺失不能证明上次删除成功；启动仍将未结束任务标为 `Interrupted`，不自动续删。

## 组件接口

主要源码：[CleanupJournal.cs](../../src/CClean.Core/Cleanup/CleanupJournal.cs)、[CleanupManifestCodec.cs](../../src/CClean.Core/Cleanup/CleanupManifestCodec.cs)、[CleanupRecovery.cs](../../src/CClean.Core/Cleanup/CleanupRecovery.cs)。以下均为同步方法，接受 `CancellationToken`；UI 应在后台读取，取消后等待实际请求收尾。

| API | 游标与返回值 | 完整度口径 |
| --- | --- | --- |
| `RunsPage(after, pageSize, cancellation)` | `CleanupRunCursor(Created, Id)`；按 `created DESC, id DESC`；`CleanupRunPage` 含 `Items / NextCursor / HasMore / IsComplete` | 可读完全部任务；游标必须与已存在任务的时间及 Id 精确匹配。旧 `Runs()` 保留明确的最近 200 次限制 |
| `EventsPage(run, afterSequence, pageSize, throughSequence, cancellation)` | 首游标为 0；`CleanupEventPage` 含 `Items / NextSequence / ThroughSequence / HasMore / RunFound / IsComplete`；`CleanupEvent` 保留四参数构造并增加 `Sequence` | 首轮固定本任务最大序号；后续必须带同一上界。负游标、超过当前任务最大值、跨任务及不属于该任务的非零游标拒绝；新事件须刷新首轮才进入读取 |
| `ManifestPage(run, afterOrdinal, pageSize, cancellation)` | 首游标为 -1，序号从 0 开始；`CleanupManifestPage` 含 `Items / NextOrdinal / TotalItems / HasMore / RunFound / IsComplete` | 按固定清单顺序读取；`NextOrdinal` 为最后返回项的序号。非法负数或越界拒绝；即使只取第一页，未知格式及坏引用也不能被尾部藏住 |
| `CleanupRecovery.InspectPage(journal, run, afterOrdinal, pageSize, throughSequence, cancellation)` | `CleanupRecoveryPage` 含 `Items / NextOrdinal / TotalItems / CheckedItems / ThroughSequence / HasMore / RunFound / IsComplete` | `CheckedItems` 是本页核查的清单项数，包括排除项；`Items` 只返回候选观测。因此必须按 `HasMore / NextOrdinal` 翻页，不能按结果数量停止；后续页保留首轮事件上界 |

所有页大小为 1～1,000，默认 200。`IsComplete` 仅等于 `!HasMore`，表示这个清单或事件快照读到末尾，不等于执行成功、活动观察完整或清理资格通过。任务不存在时显式 `RunFound=false`，不能与损坏清单混同；损坏清单抛 `IOException`，不返回假空结果。事件存在而任务缺失亦拒绝。

旧 `Events(run)`、`Manifest(run)`、`Inspect(journal, run)` 入口保留可用：事件和恢复不再静默截断，返回完整物化结果。大历史的 UI 应使用新有界分页；旧入口保留给小型兼容调用与探针。`Manifest` 与 `Inspect` 另有带取消参数的重载。

## 紧凑清单协议

新清单的顶层标记为 `Format="cclean-cleanup-manifest" / Version=1`，与保持为 1 的 SQLite 表结构版本分别管理。保留任务 Id、创建时间、上下文指纹、截断标记及全部原始对象元数据；不保存可从原始字段计算的 `Expires / EligibleCount / EstimatedBytes / Path / Status / Reason / Estimate / IsOrdinaryFile` 等重复字段。实际执行仍使用内存中原 `CleanupPlan`，历史解码只返回 `CleanupItem`，没有恢复批准的通道。

共享 `Scopes` 保存原 `RuleScope` 的六字段。共享 `Decisions` 每行是 `[Eligible, Category, Reason, ScopeIndex或null, RootIdentity或null]`。`Items` 每行依次为 `[Path, Identity或null, LogicalBytes或null, AllocatedBytes或null, LinkCount, Attributes, ModifiedTime, ChangeTime, StreamsComplete, HasNamedStreams, Exclusion或null, DecisionIndex]`。数组布局只由显式版本解释；未知版本、未知 / 重复字段、缺字段、错误类型、坏索引、重复路径、任务身份不一致和候选缺少身份均拒绝。

仍兼容旧 `Items` JSON：原完整 `CleanupPlan` 序列化与仅含 `Items` 的旧记录均可读取；原对象 / 决策必需字段会校验，存在的旧汇总还须与对象一致。新的紧凑结构不能通过去掉版本标记冒充旧结构。

写入逐段按实际 UTF-8 字节检查 8 MiB；读取在托管 `GetString` 前检查 SQLite 的 BLOB 字节长度，再由 codec 重验。预算仍按实际持久文本的 `bytes × 3 + 65536` 预估，不放宽 DB / WAL / 总预算。为了避免每翻一页重建全部对象，Journal 只缓存最近一份已校验的不可变清单，同时比较持久文本及任务身份，外部内容被改坏时不沿用旧缓存。

这是整份 8 MiB 有界文档的首次校验与单份缓存，**不宣称首次解码只占一页内存**。事件采用 SQLite keyset 与最多一页加一条的结果读取。恢复按 OrdinalIgnoreCase 路径集合流式扫描固定上界内的事件，只保存本次需要的最后状态；不在每页建立全部事件映射，也不对每项重新 `LastOrDefault`。完整兼容核查为 `O(事件数 + 清单项数)`；分页核查最坏仍为 `O(事件数 × 页数 + 清单项数)`，分页输出有界不能证明全量遍历已线性。为保留 .NET 的 OrdinalIgnoreCase，不使用仅覆盖 ASCII 的 SQLite 内置 NOCASE 代替对象路径匹配；归一化存储 / 索引或跨页快照缓存未在本轮增加，是否需要优化留待 R1-006 的实际页延迟测量。取消在读取行和元数据读前后检查，不能承诺中断已经开始的原生元数据读取或 SQLite 调用；退出必须等待收尾。
