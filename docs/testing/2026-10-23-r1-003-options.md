## 2. 自身 Deleted 与父 Changed：目前能证明到哪

实际链路是：`CleanupExecutor` 复核批准根和文件身份 → 持久化 `Started` → 同句柄删除标记成功 → 关闭句柄 → 持久化 `Deleted` → 重新读取上下文。真实 watcher 同时报告具体样本 `Deleted` 和父目录 `Changed`；后者进入 `LastActivity`，使下一项指纹失效。

对于**具体文件的删除**，一条带卷和文件身份的原生删除记录，有可能与“同身份句柄已删除、结果已落盘”的回执严格匹配。当前 `FileSystemWatcher` 只提供路径，尚无这条完整证据链。即便未来能匹配文件删除，匹配也只覆盖该对象和该次成功操作，不覆盖同路径的新对象、父目录或整个清理期间。

对于**父目录的 Changed**，子文件删除会改变目录元数据，但同一目录还可能被外部程序改时间、属性或内容。`ParentFileId` 相同、通知时间接近、清理后扫描没有新增内容，都不足以排除外部瞬时创建/删除或同类元数据修改。父目录本身通常不是批准删除对象，不能把子项批准扩大为父目录活动豁免。

USN 增加文件引用号、父引用号、原因位和 journal 游标，仍不是操作来源凭证：

- Microsoft 明确说明，同一文件在一次打开至最后关闭之间，同类修改可合并，后续同类写入可能不生成新记录；最终 `CLOSE` 是汇总，不保留全部操作顺序。[S1][S2]
- `USN_REASON_BASIC_INFO_CHANGE` 包含属性或时间戳变化；它没有“由哪个子项删除引起”的因果字段。`FILE_DELETE` 也不包含 PID 或清单 ID。[S2]
- 将 `ReturnOnlyOnClose` 设为 0 能尽早取到记录，不能取消原因位合并。只取关闭记录会进一步延迟看见长寿命句柄中的活动。[S1][S3]
- `SourceInfo` 是数据管理等来源标记，不是可信的当前执行器身份，不能以相同标记证明归属。[S2]
- watcher 的“没有报告溢出”与 USN 的“游标可读”都不是完整的进程归因保证；USN 不能修复所有通知缺口，也不能自动证明原本未知的消费者已停止。

因此，**“完整 USN 游标 + 只看见一个批准删除”目前仍不足以直接豁免父 Changed**。尤其要对抗：父目录或某外部文件的长寿命句柄已累计 `BASIC_INFO_CHANGE`/`DATA_OVERWRITE`，本次又发生同类变化而没有新的独立原因记录。观察到不匹配或无法界定的事件时必须保持未知。

## 3. 若前置 C，最小诊断包是什么

只研究已登记、已批准 fixture 的 NTFS 根；先选一个平面样本父目录，再覆盖嵌套目录。读取**现有** journal，不创建、扩大、删除或重建它；不读取用户文件内容，不采集全机进程归因，不自动要求管理员权限或安装常驻服务。权限、文件系统或 API 不支持时直接记为未覆盖，不能降级为路径匹配豁免。当前权限下哪些 API 可用仍须 PoC 核验，不承诺普通模式一定可读。[S4]

第一步只输出诊断，不改变 `Activity()` 和执行资格：

1. 在原有真实 watcher 旁读取 `ReadDirectoryChangesExW` 的扩展记录，记录具体 `FileId/ParentFileId`、类型、时间和通知完整性；扩展记录仍无 PID。[S5][S6]
2. 对相同卷查询 `JournalId/FirstUsn/LowestValidUsn/NextUsn`，保存游标边界，顺序处理所有需要的原因，不只筛 `FILE_DELETE` 或 `CLOSE`。USN 是流偏移，不要求数值逐一递增。ID 改变、游标过期、读失败、记录版本/长度无法解析均中止证明。[S3][S4]
3. 从**同一个已打开的文件句柄**建立当前 `FileSnapshot.Identity` 与原生文件引用号的映射；当前身份是卷与 128 位 File ID 加创建时间，不能把 USN V2 的 64 位引用号与旧十六进制字符串直接等同。父身份也独立读取并固定。
4. 记录预览前、逐项前、删除标记后、句柄关闭后和审计提交后的原始事件与 USN 变化。诊断分清“文件删除匹配”“父变化有解释但未证明”“存在外部或未知变化”，不输出伪造的来源结论。
5. 证明查询范围能覆盖根内的新建、嵌套、移入/移出和瞬时对象。journal 按卷读取；若根归属映射遇到未知父引用，不能仅按文件名过滤掉它。读取成本、范围外元数据处理与丢弃策略须单独记录，不能悄悄变成全机活动索引。

## 4. B 可先做：清单减重的实际离线计量

读取已完成隔离运行 `5793d529-bfc4-4054-bb03-4caee13d8523` 的 1,000 项原审计 manifest，在内存投影以下候选格式：

- 头部保留清单 ID、原创建/到期时间、原上下文指纹、截断状态及 schema；批准根、根身份、规则完整字段和分类/原因文本按完全相同值去重。
- 项目保留相对路径、原完整文件身份、逻辑/分配量、链接数、属性、原修改/变化时间、数据流完整性、命名流标志、排除原因及决策引用。
- 去掉 `Path/Status/Reason/Estimate/EligibleCount/EstimatedBytes/IsOrdinaryFile` 等可从已保存字段重建的重复显示属性；没有省略执行前校验字段，也没有用文件名替代身份。
- 离线脚本将超过 JavaScript 安全整数范围的 FILETIME 作为原十进制字符串保存，避免损失精度；未来 C# codec 必须做严格 Int64 解析，不经浮点转换。

计量结果：原 UTF-8 JSON **1,421,297 B**；候选 JSON **229,906 B**，约减少 **83.8%**；共享头部 **907 B**，本 fixture 每项平均约 **229 B**。全部 1,000 项的文件校验字段、完整 `ProtectionDecision` 和根身份都逐项还原比较成功。这里测的是离线候选编码字节，不是 C# 新 codec、执行吞吐或安装版内存。

原 manifest SHA-256：`5b7ce4fa2bf75f62b90d422129f7ac71f0f0bc0542bd7ca1a70697b4f4d168be`。读取使用 Node 24.20.0 内置 SQLite，最终以 `file:.../cleanup.db?mode=ro&immutable=1` 打开已经关闭的隔离库；计量前后主库 SHA-256 均为 `93873944e3c4871cbbf7ab0b15cc36a270859fb30a58ccb7448710bdfd71feea`，目录清单、长度与修改时间相同。

首次尝试仅设 `readOnly=true` 时，SQLite 自动生成了 0 B `cleanup.db-wal` 和 32 KiB `cleanup.db-shm`；主库长度/修改时间未变。发现后停止该次断言，改为上述 immutable 读取。自动生成的 sidecar 保留，没有清理。**immutable 仅适用于这个已关闭、已完成 checkpoint 的隔离库，不用于正在写入的生产审计库。**

### 4.2 普通工程优化的最小落点

1. `CleanupPlanner.cs` / 必要时单独的 `CleanupManifestCodec.cs`：只为持久化建立 versioned DTO，不直接序列化 UI record；共享根/规则/原因表；保留完整对象集合和当前有效期。路径重建严格拒绝绝对路径、越界、歧义和无效表索引，并保留原路径大小写。执行仍核验最终句柄路径、身份与完整元数据。
2. `CleanupJournal.cs`：按实际 UTF-8 字节在分配大字符串前有界编码，限制 8 MiB；仍先持久化整个本批，再开始首项。读取同时支持旧 manifest，不把升级当成自动恢复批准；schema 迁移事务失败回滚，高版本拒绝写入。
3. `CleanupJournal.Events()` / `CleanupRecovery.cs`：增加有界分页与总数/完整性；恢复覆盖整个批准批次，把逐项 `LastOrDefault()` 改为按项最后事件映射或有界查询，避免二次方扫描。只读完整记录，重启仍不续删。
4. `CleanupCandidateScanner.cs`、`WorkspaceViewModel`、预览/历史页：复用有界扫描和 SQLite 保留状态，实际容量按字节、时间与资源收口；页面分页不扩大批准集合，下一批重新预览确认。具体保留项跨批继续排除。
5. 先做 1,000 项 codec 还原与旧历史读取，再测 5,000/10,000 规模；并测 DB/WAL/SHM/日志预算、逐项持久化吞吐和取消。必要时审计事件引用本批不可变项序号，避免重复路径，但不删除逐项结果、意图或原原因。

这些不需要用户再批准一个抽象“大批量能力”。它们在既有 R1-006/008 的工程范围内；未满足 R1-003 观察出口前，不能让新容量进入真实用户文件执行，也不提前改该任务为 passed。

## 5. 不变门槛与必须补的验证

保持：已验证规则/用户具体确认、根和文件身份、同句柄删除、特殊/多链接/ADS 保护、活动/未知保护、固定本批禁止追加、5 分钟不续期、8 MiB、工作集 ≤ 200 MiB、DB/WAL/SHM ≤ 300 MiB、日志 ≤ 50 MiB、审计失败停止、取消只停后续项、重启不续删。原 30 分钟/转储 48 小时等规则条件也不改变。用户现有文件仍需另行具体清单确认。

归属出口至少补以下对抗场景，不能只要求三个顺序删除成功：

- 在同父/不同父、根内嵌套目录中连续三个及多个批次删除；通知提前、延迟、重复及与审计提交交错。
- 第二项前外部写入、同路径替换、消费者变化；扫描间瞬时创建/写入/删除、移入后移出，以及未知父引用。
- 直接改变父目录时间/属性；父目录或其他文件长寿命句柄中的重复同类 USN 原因；最后关闭延迟到本批以后。无法排除时保持未知。
- 活动发生在批准对象以外；同路径新身份、File ID 复用/卷变化、父目录替换、watcher 重建、范围暂停/移除或观察代次改变。
- 实际通知队列/原生溢出与受控故障分别记录；USN 被禁用/重建/裁剪、游标过期、权限丢失、记录版本/长度异常。不得用 USN 擦掉旧缺口。
- 删除后审计提交失败、游标/回执保存失败、明确退出或强制中断；未证实结果保持未知，不把“路径消失”当本次成功。
- 新鲜进程真实上下文的 5,000/10,000 项预览、确认等待、执行、历史分页与全批恢复；跨批保留、取消 ≤ 2 秒目标、真实到期点、审计增长与峰值内存。

## 6. 用户实际需要决定的事

**只有一个当前范围取舍：是否将原延期的 NTFS USN/扩展通知诊断窄化后前置到首批，用于研究上述自身变化归属。** 建议允许的最大边界是：隔离 fixture、读取已有 journal、无提权强依赖、无 journal 配置写入、无全机归因、无生产事件豁免；先提交能否证明父 `Changed` 的证据，再决定产品接入。

如果不前置，继续 A+B 及不依赖它的范围/页面工作，明确连续清理和首批总验收仍受阻；不将受限结果包装为首批完成。如果前置但证据仍不足，结果仍是 fail closed。更严格的父目录写入租约、改变活动保护语义、增加有效期或单次全集授权，均不包含在这一决定中。

普通 DTO/分页/恢复复杂度优化、初次选择 10,000 为复测候选等工程事项由开发按证据推进，不为它们再发问卷。本文没有修改旧 ETW/USN 的 deferred 状态或任何计划依赖。
