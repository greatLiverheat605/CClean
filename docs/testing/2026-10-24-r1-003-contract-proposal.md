## 3. B 的具体提案边界

### 继续保留的条件

1. 对象必须属于用户启用且独立验证的规则，具有具体用途、重建依据和处理影响。仅作用于已确认有限清单；新文件、报告、索引、实验标记、用户保留项、未知内容与清单外对象不加入。
2. 开始前仍检查当前观察完整度、已知消费者、相关项目/会话与保护范围；已知活动、能力缺失或观察故障不允许以用户点击强行绕过。
3. 执行仍按具体根与文件身份、路径边界、元数据及特殊对象条件重新核验；按验证过的同句柄方式处理，发生不兼容共享、身份/属性变化或无法检查时跳过或停止。
4. 已知消费者启动、可定位到相关范围的新建/数据写入/重命名、未批准对象删除、观察丢失、规则或范围变化仍使相关执行停止。具体事件分类与边界必须实现并接受对抗验证，不能仅列文字便认为满足。
5. 原始通知继续记录，观察状态与执行决策分开；不得伪造“这些通知确定由 CClean 产生”，也不能关闭 watcher 或全局忽略活动。
6. 保留 5 分钟有效期、8 MiB 清单、逐项持久审计、预算、取消和重启不续删。超过资源/时限保持未完成，不通过静默续期处理。

### 明确改变的条件及剩余风险

候选处理回执已经确认的对象所对应的删除通知，以及单独出现的父目录元数据通知，**不再要求先证明其唯一来源**。它们保持来源未确定；在重新核验剩余批准对象、规则和消费者条件后，新契约可以允许继续。

这不是证明没有外部活动：外部程序的属性操作或其他相关活动可能与上述通知混合，候选当时通过对象检查也不能证明没有未知消费者需要它。因而 B 不再承诺“任何无法解释的相关通知都能立即停止整批”，可能对未被识别的消费者造成缓存缺失、重建或运行失败。不能将风险省略成“只是忽略无关的父目录变化”。

首个验证对象优先使用自建、可再生成的 benchmark 样本；npm 内容/索引完整性、消费者重建与转储保留策略分别验收。某一规则通过不代表其他规则能沿用相同活动处理。

## 4. 若用户选择 B，执行出口

先在正式计划中标记安全契约变更及对原验收的影响，再按对应测试实施，不倒写旧失败为通过。

| 验证组 | 必须给出的结果 |
| --- | --- |
| 连续清理 | 真实 watcher 与动态上下文下完成多个批准对象，原始通知仍在；不再用固定合成上下文替代 |
| 已知危险变化 | 新写入、同路径替换、新增/删除未知对象、消费者变化、缺口/故障、审计失败使后续处理按约定停止 |
| 特意保留的反例 | 外部父属性修改与已批准删除交错时，明确记录新契约可能继续；不得把它改名为“未发生外部活动”或隐藏剩余风险 |
| 文件竞争 | 对象属性、内容、链接/数据流与父路径在检查前后变化；逐项验证实际访问/共享条件，不能由目录租约推导子树锁定 |
| 规则价值 | benchmark 保留资料并可重建；npm 保留组合可用并完成真实消费者重建；转储最新/48 小时规则不变 |
| 操作规模 | 独立验证 1,001 / 10,000 个真实自产对象的清单、执行、审计/恢复和资源，再决定是否提高 1,000 上限；编码能容纳 10,000 项不等于容量已验证 |

安装版、完整键盘/多 DPI、实际用户理解、资源和 72 小时观察继续验收。新契约失败时保留失败及当前独立成果，不能退回按路径/时间冒充归因证明。
